# ADR 0001: Rust execution with a Python compatibility boundary

Status: Accepted for the initial milestone

## Context

The motivating comparison showed that a fast validator could miss results when
it did not implement SPARQL targets and SHACL-AF rules. The proposed project is
a Rust implementation that can retain pySHACL behavior. pySHACL 0.40 added an
Oxigraph data backend, so both the RDFLib and Oxigraph configurations are relevant
baselines. A language rewrite alone is not evidence of a performance gain.

## Decision

1. Keep shape compilation, target selection, rule execution, constraints and
   report construction in a standalone Rust crate. Python handles only the API
   boundary. Use Oxigraph for RDF storage and SPARQL, with prepared queries.
2. Pin pySHACL 0.40.1 as the differential reference. Compare complete RDF report
   graphs, output data graphs and mutation/error semantics. Explicitly track
   differences; do not silently normalize away a missing result.
3. Write regression tests before fixing behavioral defects. Include independent
   standards fixtures so agreement with pySHACL alone is not treated as proof of
   conformance.
4. Implement a bounded first milestone: advanced targets and SPARQL rules feeding
   a small constraint set. Raise hard errors for unsupported executable features
   and invalid shapes. Do not fall back to Python or silently ignore features.
5. Preserve RDF blank-node identity across the boundary, including shared identity
   between a report and data newly generated by rules. Do not use Oxigraph's
   convenience loader when it would rename caller-owned blank nodes.
6. Keep compiled shapes reusable and per-call data independent. Apply Python
   `inplace=True` changes only after successful execution. The direct Rust API
   explicitly receives a mutable-by-interior-mutability Store and can leave its
   additions in that Store on execution error; callers control its transaction.
7. Benchmark only after report parity checks, with conversion and output costs
   included. Keep measurements and claimed coverage tied to the tested workload.

## Consequences

This milestone is not a drop-in pySHACL replacement. Generated message text,
exception classes and a large part of the feature surface remain outside its
compatibility contract. Complete Core, SHACL-SPARQL constraints, broader AF,
inference and datasets require additional independent tests and implementation.

The engine is reusable by a Rust caller without Python. There is no runtime
dependency on pySHACL. The Python import is `pyshacl_turbo`, avoiding installation
conflicts with the reference package during differential development.
